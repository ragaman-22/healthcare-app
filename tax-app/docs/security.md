# セキュリティ確認（security.md）

第8段階で実施したセキュリティ確認の結果と、運用上の方針。

## 1. 確認結果と対応

| # | 確認項目 | 結果 | 対応 |
|---|---|---|---|
| S-1 | 依存パッケージの既知の脆弱性 | **Next.js 16.2.9 に重大な脆弱性**（Proxy の認証チェックの回避、Server Actions の DoS、画像最適化の RCE など）。開発用の Vitest にも脆弱性 | Next.js を 16.4.2、Vitest を 4.1.12 に更新。`npm audit` で 0 件。CI で `npm audit --omit=dev --audit-level=high` を実行 |
| S-2 | 本番でのデモモード | Supabase の環境変数の設定漏れで、本番がログイン不要のデモモードになる可能性 | 本番（`NODE_ENV=production`）では `ALLOW_DEMO_MODE=true` のときだけデモを許可。それ以外はログイン画面のみ |
| S-3 | デモのメモリ使用量 | デモの帳簿・画像はサーバーのメモリに保存されるため、大量登録でメモリを圧迫できる | 同時セッション200件（古い順に破棄）、1セッションあたり3,000件・画像30枚の上限 |
| S-4 | エラーメッセージ | データベースのエラー内容（テーブル名・制約名）を画面に表示していた箇所がある | 業務上のエラー以外は一般的な文言にし、詳細はサーバーのログのみに出力 |
| S-5 | 新規登録のエラー | 「登録済み」と表示するとメールアドレスの存在確認に使われる | 一般的な文言に変更 |
| S-6 | DB の関数の実行権限 | PostgreSQL は関数の実行権限を全ロール（PUBLIC）に付与する。未ログイン（anon）からアプリの関数を呼べた（各関数で `auth.uid()` を確認しているため実害はないが、多層防御として不十分） | PUBLIC・anon から実行権限を取り消し、authenticated・service_role に付与。DB テストで「anon が実行できる関数が0件」を確認 |
| S-7 | DB テストの前提 | テスト環境がマイグレーション後に関数の権限を一律付与しており、マイグレーションの `revoke` を打ち消していた | Supabase と同じく、マイグレーション前に既定の権限を設定する方式に修正 |
| S-8 | RLS | 全テーブルで RLS が有効か | DB テストで `public` スキーマの全テーブルを検査（無効なテーブルがあると失敗） |
| S-9 | security definer の関数 | search_path の固定 | DB テストで、search_path を固定していない security definer 関数が0件であることを確認 |
| S-10 | HTTP ヘッダー | 未設定 | CSP（`frame-ancestors 'none'`・`object-src 'none'` など）、`X-Frame-Options: DENY`、`X-Content-Type-Options`、`Referrer-Policy`、`Permissions-Policy`（カメラは自サイトのみ）、HSTS、`X-Powered-By` の削除。E2E で確認 |
| S-11 | デモの Cookie | 本番で `secure` が付いていない | 本番では `secure`、有効期限を30日から7日に短縮 |
| S-12 | CSV の書き出し | Excel で数式として実行される値（`=` `+` `-` `@` で始まる）を含む可能性 | 先頭に `'` を付けて無害化（単体テストあり） |
| S-13 | 検索エンジン | 帳簿の画面がクロールされる可能性（ログインが必要なため内容は出ないが） | `robots.txt` でログイン画面・規約以外を除外 |

## 2. 確認済みの仕組み（変更なし）

- **認証・認可**: proxy でセッションを更新・未ログインはリダイレクト。各ページ・Server Action でも `requireUser()` で再確認。DB は RLS で本人の行のみ
- **編集対象の ID**: 新規作成の ID はサーバーで発行。編集時は本人のデータであることを確認（DB の保存関数でも、他人の ID と衝突した場合はエラー）
- **ファイルのアップロード**: 先頭バイトで画像形式を判定（拡張子・Content-Type を信用しない）、5MB 上限、Storage は非公開バケット・本人のフォルダのみ、画像は認証付きのルートから `nosniff` で配信
- **秘密情報**: `ANTHROPIC_API_KEY`・`SUPABASE_SERVICE_ROLE_KEY` はサーバー専用（`server-only` のモジュールからのみ参照、`NEXT_PUBLIC_` を付けない）
- **オープンリダイレクト**: メール確認の戻り先はサイト内の相対パスのみ
- **CSRF**: Server Actions は Next.js の Origin 検査、Cookie は `SameSite=Lax`
- **AI の出力**: 構造化出力＋サーバー側の検証。勘定科目は利用者が使える費用科目のみ。利用者の確認なしに帳簿へ反映しない
- **監査**: 取引・仕訳・申告設定・締めの変更前後を `audit_logs` に保存（利用者は変更・削除不可）

## 3. 残っている課題

| 課題 | 内容 | 予定 |
|---|---|---|
| CSP の `unsafe-inline` | Next.js のインラインスクリプトのため `script-src 'unsafe-inline'` が必要 | nonce 方式（proxy で nonce を発行）に移行 |
| ログインの試行回数制限 | Supabase Auth のレート制限に依存 | Supabase の設定（CAPTCHA・レート制限）を本番で有効化 |
| 多要素認証 | 未対応 | Supabase Auth の MFA（TOTP）を検討 |
| 脆弱性診断 | 第三者による診断は未実施 | 公開前に実施 |
| 監視 | エラー監視・不正アクセスの検知が未設定 | Vercel のログ・Sentry などを導入 |
| ログインアカウントの削除 | `SUPABASE_SERVICE_ROLE_KEY` がない場合、データは削除されるがアカウントは残る（画面で案内） | 本番では管理者キーを設定する |

## 4. データの保管・バックアップの方針

- **Supabase のバックアップ**: 有料プランの日次バックアップ（必要に応じて Point-in-Time Recovery）を有効にする。復元手順を公開前に一度試す
- **利用者による書き出し**: データ管理画面から、全データ（JSON）と仕訳帳（CSV）をいつでも書き出せる。帳簿の保存期間（原則7年）を考え、年に一度の書き出しを案内する
- **削除**: データ管理画面から、全データ（画像を含む）とログインアカウントを削除できる。バックアップからの消去までの期間をプライバシーポリシーに記載する
- **画像**: レシート画像は Storage に保存。電子帳簿保存法の要件（検索・改ざん防止など）は別途確認が必要
